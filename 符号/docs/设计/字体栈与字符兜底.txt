字体栈与字符兜底

双模字符
	同一个码位可能有多种呈现。☺ ♥ ▶ ▪ © 这类字符既能走文本形态（单色），也能走 emoji 形态（彩色）。
	本页的选择：让它们默认渲染成单色，跟普通文字一致。要彩色得显式加变体选择符 U+FE0F。

没有字体覆盖全部 Unicode
	本页字体栈里六个字体的实际覆盖（读字体文件的 cmap 表，2026-09-16 实测）：
		Arial  3,506 码位  2.34%
		Segoe UI Emoji  2,025  1.35%
		Segoe UI Symbol  7,536  5.03%
		Consolas  2,489  1.66%
		Lucida Sans Unicode  1,753  1.17%
		Noto Sans Symbols 2（页面自带）  2,955  1.97%
		六个加起来（并集）  11,411
	参照：Unicode 15.1 已分配码位共 149,813。
	各字体补了哪些别家没有的（独有贡献，同一算法实测）：
		Segoe UI Symbol  3,563
		Arial  1,127
		Noto Sans Symbols 2  601
		Segoe UI Emoji  226
		Consolas  8
		Lucida Sans Unicode  0  →  纯冗余，它覆盖的 1753 个码位其余五个全都有。todo：以后从栈里去掉
	六个加起来才一万出头，所以渲染一个字符要按顺序问一排字体，谁先有字形就用谁。这就是字体栈。

栈穷尽之后：系统字体链
	栈里六个都没有字形时，浏览器还会继续往系统字体链里找——按字符所属的文字系统挑一个系统默认字体。这一段在栈外，页面控制不了，但得知道它存在。
	本机实测命中（2026-09-16，字体栈与页面完全一致，lang="zh-CN"）：
		中 / あ  →  Noto Sans SC
		한       →  Malgun Gothic
		ཀ        →  Microsoft Himalaya
		ก        →  Tahoma
		𠀋       →  SimSun-ExtB
	规模：本机 229 个字体文件合起来覆盖 154,279 个码位，其中 142,868 个（92.6%）是栈覆盖不到、只能走系统链的。按类别：
		汉字（统一表意 + 扩展 A/B/C-F/G-H）  97,064  68.0%
		谚文音节（韩文）                      11,184   7.8%
		彝文、藏文、泰文、天城文等各语种文字
		少量符号与变体选择符
	所以「中文能正常显示」不是这个字体栈的功劳，是系统链兜的——换一台没装中文字体的机器就会全是豆腐块。
	反过来，阿拉伯文、希伯来文、希腊文、西里尔文其实都在 Arial 里，属栈内覆盖，不需要系统链接手（实测 ا 命中 Arial）。

浏览器怎么用字体栈
	font-family 给一串字体名，浏览器从头逐个问「你有这个字形吗」，用第一个有的。
	「泛型」（sans-serif / serif / monospace）不是某个具体字体，是让浏览器取系统默认。浏览器拿到泛型会展开成一条系统回退链，而不是当成一个普通候选。
	所以如果把泛型放开头，后面显式列的字体永远轮不到——泛型自己就把字符消化掉了。

	这件事的具体机制（本机实测）：系统回退链按文字系统挑默认字体，中文挑的是 Noto Sans SC。它覆盖 30,890 个码位，除了 20,976 个汉字，还顺手包含了杂项符号区 U+2600-27BF 的 88 个和 CJK 符号区 U+1F200-1F2FF 的 58 个——⚽ 🈚 🆎 🉑 就在里面，而且它们都不在 Arial 里。
	所以泛型打头时，这 146 个符号被 Noto Sans SC 拿走渲染成单色，后面显式列的 emoji 字体永远轮不到。
	它不碰真 emoji 区（U+1F300-1FAFF 覆盖 0 个），所以 😀 🏀 这类一直正常——问题只藏在那一百多个符号里，小到不容易被发现。这也解释了为什么"系统文字字体也覆盖的那批 emoji"才会出问题。

	栈的顺序：
		1 一个文字字体打头。它不含 emoji 字形，双模字符留在文本形态，真 emoji 继续往下落。
		2 系统 emoji 字体。
		3 系统符号字体。emoji 字体必须排在它之前，否则双模字符在此被现实为单色模式。
		4 页面自带的符号字体。
		5 泛型兜底。

	设计生效的实测证据（同一批测量里取的）：
		☺ → Arial          双模字符落在文字字体上，没被 emoji 字体抢走
		⚽ → Segoe UI Emoji  emoji 正确落到 emoji 字体
		😀 → Segoe UI Emoji
	列表区和详情区共用同一个栈，两区渲染一致。栈的权威值在页面脚本里，挂载时写入；样式表里那份是挂载前的兜底，改栈时两处要同步。

页面自带的字体
	符号页随页面加载一份覆盖很广的符号字体，放在栈里紧挨泛型之前。
	效果：系统里没有的符号，本页也能显示。
	注意别把它想成「用户装的」——它是随页面来的，对方打开本页自动就有。只有把字符复制到本页之外去用，才需要对方自己装字体。

渲染不出来时的两条提示
	判断两件互相独立的事：
		系统默认字体链能不能渲染——不含页面字体栈，问的其实是「复制到别处还看得见吗」
		页面自带的字体收录了它没有
	组合出两条提示，互斥，永不同时出现：
		自带的也没有 → 「当前字体不支持」，显示在名字下方
		自带有、系统渲染不出 → 说明本页用自带字体显示，显示在名字上方
	第二条是推出来的：系统链渲染不出而自带有，说明栈里排在它前面的那几个系统字体也都不行，渲染一定靠它。
	实测：U+1F900、U+1FA00（国际象棋符号）会触发提示；系统能渲染的（如 U+1F600）两条都不出现。

详情区的字体切换
	详情区可以手动选一个字体预览。**选中后强制只用那个字体，不走栈、不走 fallback**——这样切换才看得到真实效果，否则没覆盖的字符被栈兜住，看不出差别。
	「加载本机字体」只扩充可选的列表，**不改渲染栈**。

判定要看实际渲染结果
	查字体的收录表只能知道「有没有收录」，回答不了「渲染出来是不是豆腐块」。
	做法是拿保证没有字形的私有区码位当参照比出豆腐块模板，再逐像素比对。
	⚠️ **canvas 里量 ≠ 页面里渲染**：canvas 的字体属性对超长 font-family 列表解析异常。检测必须用 DOM 探针。
	⚠️ **浏览器缺字形会自动 fallback，几乎不显示 .notdef**——所以"强制只用某字体"时，未覆盖的字符显示的是系统兜底字形，不是豆腐块。

已知遗留
	Unicode 16/17 有 7 个 emoji 字符，本机这六个字体一个都没有，必然显示为豆腐块：
		🛘 U+1F6D8 滑坡
		🪊 U+1FA8A 长号
		🪎 U+1FA8E 宝物箱
		🫈 U+1FAC8 多毛生物
		🫍 U+1FACD 虎鲸
		🫪 U+1FAEA 扭曲脸
		🫯 U+1FAEF 打斗云
	这是字体没收录，不是栈排错。

	另一件：本机把 Noto Sans Symbols 2 也装进了用户字体目录，所以系统链也可能命中它。在这台机器上验证「系统没有、靠页面自带字体显示」是不可靠的，要去没装该字体的机器上验。

改这块时注意
	要查某字符实际命中哪个字体，用浏览器调试协议的字体查询。document.fonts.check() 不能用：它装的是页面用 @font-face 声明过的字体，字体名不在这个集合里就直接返回 true，而系统字体从来不在集合里。
	字体回退问题要用本机真实 Chrome 验证。自动化测试自带的 Chromium 版本固定，与本机 Chrome 版本不同；字体回退行为随 Chrome 版本变过，会得出相反结论。
	字体查询返回的字形数不能判豆腐块：缺字形时它报的是该字体的 .notdef，照样是「1 个字形」（实测 🛘 报 Arial [1 字形]，其实是豆腐块）。
	渲染宽度等于一个字符宽不等于豆腐块——全角字符本来就占一个字符宽，那是正常字形。
	改完 bump 页面资源版本参数（惯例 ?v=YYMMDD），否则浏览器拿缓存。
