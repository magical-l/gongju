## 1. 优化 27：NFKC 展开式当字符别名 + 同形字

### 1.1 目标

让搜索能靠「等价形式」命中字符，而不是靠名字里恰好出现那几个字母：

| 搜索 | 应命中 | 为什么现在不行 |
|---|---|---|
| `xii` | `Ⅻ` (U+216B) | 它的名字是「罗马数字12」，里面没有 `xii` |
| `m2` | `㎡` (U+33A1) | 名字是「平方米」 |
| `kg` | `㎏` (U+338F) | 名字是「千克」 |
| `μ`（希腊） | `µ` (U+00B5 微符号) | 名字是「微符号」 |

### 1.2 关键设计决策：**NFKC 只碰数据，不碰用户输入**

这是整件事的核心，也是被否决方案的分水岭。

**做法**：给字符**发小名**（追加 `alias`），NFKC 只用来算这些小名。
- 用户打 `①` → 就搜 `①`，直接跳到 U+2460（字面通道保持原样）
- 用户打 `1` → `①` 因为小名是 `"1"` 而成为**众多命中之一**（实测只 +60 条，0.87%）

**被否决的做法**：把用户的查询词 NFKC 化。那会让搜 `①` 变成搜 `1`，从「精确 1 条、直接跳详情」变成「3181 条里翻」。同理不可用 `normalize('NFKC')` 去折查询词。

**为什么不用 NFKC 折查询词的硬数据**：数据里 51704 个单码位字符，**4866 个（9.4%）会被 NFKC 改写成别的字符本身**——

```
① U+2460 → U+0031        ㎏ U+338F → U+006B U+0067
Ⅻ U+216B → U+0058 0049 0049   ㍿ U+337F → U+682A 5F0F 4F1A 793E
```

而「打一个字符直接跳到它」是本工具的核心交互。

### 1.3 机制：别名注入，**搜索代码零改动**

别名写进 `符号富化数据.js`（人工富化层）。

已验证这条路径通：
- `buildSymbolMap` 的注释原文就是「SYMBOLS 为**旧数据富化源**，first-wins」
- **顶层 `{char, name, alias}` 形态本来就存在**（42 条，如 `{"char":"Ü","alias":["U分音"]}`）——给字符补别名不用建组
- 搜索的 `meta.aliases.some(a => widthIncludes(a, q))` 已经认它，**一行搜索代码都不用改**

### 1.4 数据来源

| 来源 | 要不要下载 | 说明 |
|---|---|---|
| NFKC 展开 | **不用** | 它是 `参考资料/UnicodeData.txt` 的 `Decomposition_Mapping` 字段，**项目已有**。Python/JS 的 `normalize('NFKC')` 就是照它算的 |
| UTS #39 confusables | **要下载** | `https://www.unicode.org/Public/security/latest/confusables.txt`（6565 条，版本 17.0.0，和项目 UCD 版本一致），放 `符号/参考资料/` |

> 探路时已把 `confusables.txt` 下到 `C:\Users\lwj\AppData\Local\Temp\confusables.txt`，还在就直接用，不在就重下。

### 1.5 表规模与噪音（已跑过模拟，数字可直接引用）

- **表规模**：5026 个字符 / 5978 条等价形式 / **86 KB**
- **噪音**（全表 5.1 万字符扫描）：

| 查询 | 现在 | 加表后 | 增量 |
|---|---|---|---|
| `xii` | **0** | **2** | +2 |
| `m2` | 6 | 11 | +5 |
| `kg` | 2 | 2 | +0 |
| `1` | 6920 | 6980 | **+60（0.87%）** |
| `a` / `ok` / `fi` / `in` | — | — | **+0** |

**结论：噪音极小，不需要排序引擎。**（以前我误以为「搜 1 会淹掉」，那是把「NFKC 折查询词」和「给字符发小名」搞混了。）

- **样本**：`Ⅻ→xii`、`㎡→m2`、`㎏→kg`、`①→1`、`−→-`、`µ→μ`、`ﬁ→fi`、`½→1/2`、`𝐀→a/A`、`㍿→株式会社`

### 1.6 收窄规则（我定的启发式，可调整）

confusables 全表落在数据里的源字符有 5483 个，**收窄到「拉丁 / 希腊 / 西里尔 / 数学字母 / 圈号」子集后 1377 条**——挡掉希伯来/阿拉伯变音符那类对中文用户无意义的噪音。已在宽度折叠覆盖里的不重复收。

NFKC 展开侧要**剔掉 72 条**展开含组合符/空白的（如 `¨` → 空格 + 组合分音符），那些对搜索无用。

**分数斜杠要归一**：NFKC 把 `½` 展开成 `1⁄2`（U+2044 FRACTION SLASH），用户会打 `1/2`——构建时把展开里的 U+2044 换成普通 `/`。

### 1.7 构建脚本与落点

- 新建 `符号/build_equiv.py`（可重跑，风格照抄 `build_zh_variants.py` / `build_noto_cmap.py`）
- 产出：直接**改进 `符号富化数据.js`**（不是新建数据文件）——638 个已有条目追加 `alias`，**3154 个新建条目**
- 更新 `符号/docs/设计/数据说明.md`（数据文件表、生成脚本表）

### 1.8 ⚠️ 副作用：改名落盘路由会变

`保存符号元数据` 有一行 `const inSymbols = !isSeq && ENRICHED_SYMBOLS.some(s => s.char === sc.char);`，它决定改名写哪个文件。

新建的 3154 条条目会让这些字符从「改名写 `官方名直译名.js`」变成「写 `符号富化数据.js`」。

**这是期望行为**，用户明确表过态：「我在页面上给它们改名，本来就应当是去符号数据里的，不是去改官方名直译。」但要知道有这个变化。

## 2. 数据清理 29：CLDR 俗名的分层搬移

### 2.1 目标

`官方名直译名.js` 现在混了一批**不是译名**的东西。按「名字表只装官方英文名的机械直译、俗名归人工层」的分层原则，把 CLDR 俗名搬进 `符号富化数据.js`，把真正的直译补回名字表。

### 2.2 现状（实测）

`官方名直译名.js` 的 37396 条单码位名里，**1613 条与 CLDR 值相同（约 5%）**。按区段拆：

| 区段 | CLDR 条数 | 性质 |
|---|---|---|
| BMP 标点/字母/数字 | 223 | **纯直译**（左花括号/破折号/顿号/倒置的感叹号）——**不用动** |
| 杂项符号 U+2600-27BF | 118 | 混，约一半是简化名（微笑/不满/红心/骷髅） |
| **补充符号/表情 U+1F000+** | **1164** | **基本全是俗名** |

俗名样本：`GRINNING FACE → 嘿嘿`、`FACE WITH TEARS OF JOY → 笑哭了`、`FACE PALM → 捂脸`、`🫠 MELTING FACE → 融化`、`🚵 MOUNTAIN BICYCLIST → 骑山地车`。

### 2.3 搬移的工作量分解（实测）

那 1164 条里：

| 情况 | 条数 | 搬移动作 |
|---|---|---|
| 符号富化数据.js 里已有条目，且俗名已在名/别名里 | 100 | 删名字表那一条即可，零新增 |
| 已有条目，但俗名没收录 | 341 | 往那条补一个 `alias` |
| **符号富化数据.js 里完全没有** | **723** | **新建条目** |

### 2.4 ⚠️ 唯一的坎：emoji 词表现在是空的

`译名词表.py` 的 `WORD` 只有 180 条、`PHRASE` 91 条，**`FACE` / `SMILE` / `GRIN` / `KISS` / `HEART` 一条都没有**——因为 CLDR 一直把 emoji 兜住了，从来没需要翻译它们。

所以「补直译」不是改几个表，是**先建 emoji 词表**。好消息是 emoji 官方英文名高度公式化（`形容词 + FACE + WITH + ...`），约 150-200 个词 + 若干短语就能覆盖大头。

### 2.5 步骤

1. 建 emoji 词表：`译名词表.py` 的 `WORD` 加约 150-200 词 + 常用 `PHRASE`（注意它的判据：**真英文词进 `ENGLISH`，记音/专名进 `_KEEP_*`，别把英文实词塞进 KEEP**——项目踩过「KEEP 误收英文词导致待译清单静默漏报」）
2. 重跑 `build_zh_translation.py` 生成 1164 条直译
3. CLDR 俗名搬进 `符号富化数据.js`：441 条补/改别名 + **723 条新建条目**
4. `官方名直译名.js` 那 1164 条换成直译

### 2.6 ⚠️ 两个注意

- **`build_zh_translation.py` 是 merge 语义**（只补没有的键、已有的不动），**别当全量生成器**。真要全量重算，得先把现有文件挪走。
- 步骤 3 的 723 条新建条目，同样触发 §1.8 的落盘路由变化。

## 5. 本项目已踩过的坑（别重复）

1. **追加 `符号富化数据.js` 条目后必须 node 逐项校验 `char`** —— 双逗号会产生稀疏空槽，`node --check` 查不出来
2. 数据文件是 `window.XXX = {...};` 包装，**写裸 JSON 会让 `<script src>` 直接 SyntaxError**
3. **别留空组**（`{"标签名": {}}` 或 `{"标签名": {"alias": []}}` 这种组壳）
4. 遍历名字表的 `names` 时**别假设键是数字** —— 里面混着序列键（含 `-`），`+k` 会得到 `NaN`
5. 改名前**两层都要扫**（符号数据的组名/条目级 name + 名字表），只扫一层必漏
6. `docs/` 下的历史决策日志**不要改**（改了等于篡改历史）
7. 数据文件每行一条、**末条不带逗号**
8. 换行风格与末尾换行**交给 `write_text` 自动探测**，别硬编码
9. **GitHub raw 在本机网络会被重置** —— 需要从 GitHub 取文件时直接走 jsDelivr 镜像（本轮下载 OpenCC 表时踩到）
