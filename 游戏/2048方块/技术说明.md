# 2048 方块 — 实现技术说明

本文档描述与《玩法.txt》规则对应的**实现约定**，供开发与对照测试使用；规则本身以《玩法》为准。

## 1. 棋盘存储与屏幕方向

- 二维数组 `board[r][c]`：`r = 0` 为**屏幕最上一行**，`r` 增大方向为**向下**。
- 《玩法》中的数学坐标为 **`y = 0` 在底部、`y` 增大向上**；与 `r` **相反**。讨论「靠上/靠下」时请标明用的是哪一种。

## 2. 消行 7.1 收尾：`packAfterClearedEmptyRows`

一轮 `doClearAndGravityOnly` 内，对本轮标记为**满行**并已做除法、剩格 1×1 下落的行，记集合 `clearedSet`。

收尾时**不再**使用「把所有非空行压缩到场地最底」的算法。

当前实现：

1. 自上而下扫描每一行 `r`。
2. 若 **`r` 在 `clearedSet` 中**且该行**全为 0**，则**丢弃该行**（相当于消行里被抽掉的空行）。
3. 其余行按原顺序依次保留（含：非本轮满行、本轮满行但仍有剩格/未全空的行、以及原本就全空的全空行——**建造空隙所在的全空行会保留**）。
4. 设丢弃了 `k` 行，则在结果棋盘**顶部**补 `k` 行全 0，使总行数仍为 `rows`。

效果：与经典消行一致——消掉的行消失，上方整体下移；**不会**把悬空块与下方消行区之间的全空行「吃掉」，行内建造空隙（如 `[2,2,0,0]`）随整行平移。

## 3. 剩格 1×1 下落（顺序与临时占位）

- 满行除法后，每个非零剩格单独按与 `tick` 一致的下落/合并/锁定处理。
- 实现上需避免同一轮多粒仍占原格导致路径错误：在按顺序模拟每一粒之前，会先把**本轮已收集到的剩格原位置**置 0，再依次跑每一粒（详见 `prepareLineClearDivisionPhase` + `runRemainderDropsFromSortedList`）。这是**实现手段**，不是玩法术语。
- **页面试玩**（`steppedLineClearRemainder`）：剩格**留在棋盘原位**（不先清空），每个下落周期内对所有未锁定剩格各执行**一格**下落（`tickLineClearSimultaneousRemainders`，处理顺序：行号大者优先、同列左先），实现「同时各落各的」的可读动画。
- **活动块已合并格**写在棋盘上；左右移、旋转成功后须 `syncMergedCellsForPieceTransform` 同步棋盘，避免原合并位残留成「残影」；擦除旧格时仅当 `board[r][c]===cell.value` 才置 0，避免误清固定堆。
- **占用检测**：`pieceOverlapsBoard` 在 `pieceOverlapsBoardStrict` 前用 `withMergedFootprintCleared` 临时清空己方 merged  footprint，再判非 0；否则与固定堆同数字格会误判为可穿入，旋转/踢边会「踹飞」格。
- **旋转**：`rotatePieceCells90CCW` 携带各格 `value`/`merged` 绕质心旋转再归一化。**O / S / Z** 使用 `rotatePieceKeepBoundingAnchor` 保持包围盒左上角绝对位置不变，且仅尝试 `colOffset=0`（不左右墙踢）；**T / J / L / I** 仍可用多档 `tryOffsets` 与竖向踢边。
- **硬降（DOM）**：不再用 `runUntilFirstLock` 一次跑满 tick，改为与自动下落相同的 `getFallStepMs` 间隔逐步 `tick`。

## 4. 测试场景 ⑤ / ⑥

- **⑤**：`advancePostLockLineClearNoSpawnWithStats` 统计下，区内竖合、cascade、剩格下落合并**均为 0** 的终盘。
- **⑥**：含上述任一类合并的终盘，以及脚本中**固定写入 ⑥**的用例（如「被消行上方仍有非满行」一组），与 stats 是否为 0 无关。

**期望棋盘 `expected` 的来源**：运行 `test/gen-scenario-05.js` 时，对每条用例的 `before` 调用 **`logic.js` 里的** `advancePostLockLineClearNoSpawnWithStats`（⑤/⑥ 分流）或 `advancePostLockLineClearNoSpawn`（⑥ 固定例），把返回的 `board` 写入场景文件。**不在场景数据里手填终盘**。浏览器 / Node 跑场景时再次调用同一套 `advancePostLockLineClearNoSpawn`（见 `test/runner.js`、`test/run-all-scenarios.js`），与文件中的 `expected` 比对。

⑤ 内标签含「**悬空**」的用例在生成时排在**无悬空用例之后**（仍无合并）。

⑥ 内：合并顺序为 **固定小盘 → 底双行枚举去重 →「被消行上方 / 上方非满行」等复杂固定例**；再按标签二次排序，使含「**悬空**」「**被消行上方**」或「**上方非满行**」的用例一律在**其余用例之后**（与 ⑤ 同一套直觉：简单在前、复杂在后）。

## 5. 消行「下方」与 7.2 多轮合并的语义（设计讨论）

**问题**：被消行带**下方**的固定块堆，在消行之后是否也应当做「重力式」的合并？上方失去支撑而下落，叙事上很顺；**下方**的块并没有因为消行而「失去支撑」，为什么还会跟着合并？

**说明**：

1. **消行 7.1**里「整行抽掉」只改变**上方**相对位置（+ 剩格 1×1 下落），**不是**用「下方块被往上吸」来叙事。
2. **7.2 多轮合并**（含 cascade）在规则上是对**当前整盘固定块**做「竖向相邻同数可合并」的**全局整理**，**不是**单独对「消行下方」或「失去支撑」的块做重力合并。消行结束后若某列里出现新的竖向相邻同数（例如上方整块下移、或区内竖合之后），就会进入合并/级联——这是 **2048 式**的「有相邻就合并」规则，与「这一格是不是在消行带下面」无直接因果。
3. 若场地下方是**场地边界**（最底几行消行），则**不存在**「消行下方还有块」；若消行在中间带、**下方**仍有块，**它们本身不会**因为「消行」而像上方那样**整行塌落**，但若盘面变化后**与**邻格形成同数竖合，**仍会**按 7.2 合并——这是**规则驱动的合并**，不是「下方块也受重力下落」的同一套叙事。

玩法与实现若希望**严格禁止**「消行带下方」在未发生任何位移/下落时触发合并，需要单独改规则（当前实现未做这种区分）。

## 7. 《玩法补充》草案（裁判规则 / 验收标准）

- **文件**：`玩法补充.txt`（与《玩法.txt》同目录），**纯文本**。  
- **地位**：在并入主《玩法》之前，消行后整理的裁判规则以该文件为准；与主《玩法》第七节若冲突，以验证通过后的修订稿为准。  
- **修正案（第十节）**：与主《玩法》**7.2** 全文若冲突，以修正案为准；7.2 中 `gapRow` 等仅为历史实现对照，主《玩法》正文已改为「详见技术说明」式表述。  
- **已实现（手动调试 / 分步消行）**：`lineClearPolicy.aboveRowsMode` 为 `column`（按列竖条）或 `whole`（整段一块，默认），与剩格同一拍内依次下落（`tickLineClearSimultaneousRemainders`）。  
- **已固定（非用户策略）**：`afterClearPack` 恒为 `whole`（7.1 即 `packAfterClearedEmptyRows`）；`mergeStart` 恒为 `contact`；`mergeRounds` 恒为 `untilStable`。`normalizeLineClearPolicy` 会忽略存档里旧值。  
- **修正案（第十节）与代码**：棋盘另有 `boardCellGroup`（与 `board` 同尺寸）。抠出「整块上方行」`_ABOVE_WHOLE_` 时分配 `aboveWholeGroupId`，落锁写入该组号；当 `aboveRowsMode === 'whole'` 时，竖合禁止由 `isAdjacentVerticalMergeBlockedByWholeSlab` 统一判断（消行区内竖合与全场 cascade 共用）：**①** 同列相邻两格组号相同且非 0 → 同一块内部不竖并；**②** 上格组号 &gt; 0（整块抠出所标）且下格组号为 0（盘面原有固定格）→ 不竖并，避免 U 形等「左右脚已触底与底行合并后，中间列仍与正下方满行同数在 cascade 里并掉」。竖合发生后该格组号清零。活动块下落时的同数合并仍走 `tick`，不受 ② 影响。  
- **仍与「分步消行」以外的差异**：主路径一次消行仍走 bundled `doClearAndGravityOnly`（不抠上方活动块）；若要对齐「剩格与上方块同拍」到主游戏，需再改主路径调度。  
- **后续**：主《玩法》§7.2 定稿后合并文案；主路径若要对齐补充全文，再扩展 bundled 消行。
