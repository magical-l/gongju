## 一、搜索排序：字符命中前置

### 症状（实测，读 `vm.tokenResults[0].memberSet` 的真实插入顺序）

| 搜索 | 总数 | **你搜的那个字排第几** | 排在最前的是 |
|---|---|---|---|
| `a` | 91241 | **第 78039 位** | 👯 👰 👲 👳 🤵 |
| `中` | 105637 | **第 8393 位** | 🏼 + 一堆肤色序列 |
| `马` | 590 | **第 371 位** | Ⅰ Ⅱ Ⅲ Ⅳ Ⅴ |

搜「马」第一个出罗马数字，是因为标签「数学/数字、数码/罗**马**数字」的**名字里含"马"**——子串匹配把它的 40 个成员全拉到了最前面。

### 根因

结果分节的渲染顺序 = `memberSet` 这个 Set 的插入顺序，而 `computeTokenResult` 是**先塞标签成员、再把字面命中的字符追加在后面**：

```js
const memberSet = this.memberSetOfTags(this.matchTagsStrong(token));
for (const hit of charHits) memberSet.add(memberKey(hit.cp));
```

标签通道走的是**朴素子串匹配**（一个标签名命中就把它整桶成员拉进来），字符通道才是"精确/接近精确"的。顺序反了，于是最相关的那条反而垫底。

### 修法（2 行，对调加入顺序）

```js
const memberSet = new Set(charHits.map(h => memberKey(h.cp)));
for (const k of this.memberSetOfTags(this.matchTagsStrong(token))) memberSet.add(k);
```

**只改顺序，不改集合。** 下游消费方核对过：`intersectionKeys` 按 `has`/`delete` 判成员、不依赖顺序；`intersectionHint` 只看 size；`searchSections`/`searchCardsFromKeys` 按 Set 迭代顺序出卡（正是要改的那个）。

实测（改前基线逐位对照）：

| 搜索 | 命中字符位次 | memberSet.size | 改前基线 |
|---|---|---|---|
| `a` | 78039 → **0** | 91241 | 91241 ✅ 逐位相等 |
| `马` | 371 → **0** | 590 | 590 ✅ |
| `中` | 8393 → **0** | 105637 | 105637 ✅ |

## 二、简繁兼容

### 设计：两边都折到简体，一次比较覆盖双向

`繁 → 简` 是**多对一、确定性**的，所以只要**查询词和内容都折成简体**，两个方向就同时成立：

- 繁体查询「圓圈」→ 折「圆圈」→ 命中名字「圆圈数字」
- 简体查询「干」→ 内容「乾卦」折「干卦」→ 命中

反过来「只折查询词、把它展开成变体」才是会出事的那条路：查询「开发」→ 开→開、发→發/髮 → 组合出 6 个变体，长词直接爆炸。**折内容更简单也更便宜。**

### 范围（实测，决定了这活儿有多大）

会被匹配的文本里真正含繁体的极少：

| 数据源 | 条数 | 折后变化 |
|---|---|---|
| `官方名直译名.js` 名字 | 37396 | **24 条**（21 字种：乾 優 勝 協 問 將 帥 後 敗 監 箏 終 財 販 資 車 遊 適 項 馬 鬥） |
| `符号富化数据.js` 名/别名/简介 | 5107 | **45 条**（35 字种：唸→念、帥→帅、馬→马…） |
| `标签.js` 名/简介/别名 | 1784 | **0 条** |
| `unicode官方名.js`（英文） | 53577 | 0 条 |

所以**不做"每条都折"的重方案**，改成**预折叠、只存变了的那些**：

```js
function buildSimplifiedText() {          // mounted 里 buildSymbolMap() 之后调用
    SIMPLIFIED_TEXT = new Map();          // 原文 → 简体，只存折了才变的
    ...
}
function widthIncludes(hay, q) {
    hay = SIMPLIFIED_TEXT.get(hay) || hay;   // ← 内容侧一行，全部通道自动覆盖
    ...
}
```

实跑产出 **66 条**（符号富化层 45 → 去重 43；直译名层 24；重叠 1 条；43+24−1=66）。全表约 6.9 万条里只有这 66 条会变，所以 `SIMPLIFIED_TEXT.get` 绝大多数是极快的 miss。

### 数据文件与脚本

- 源：OpenCC `TSCharacters.txt`（Apache-2.0），落在 `符号/参考资料/TSCharacters.txt`。**GitHub raw 在本机网络被重置，改用 jsDelivr 镜像取到**。
- `符号/build_zh_variants.py` 可重跑：读源 → 剔空转条目（`㑮→㑮` 这种自己映射自己的，剔掉 926 条）→ 产出 3222 条 / 58KB 的 `符号/繁简表.js`（`window.ZH_VARIANTS_DATA = {_v, map}`）。
- 表是**纯 繁→简 单向**。反向（简→繁）按设计不做——一对多有歧义，且由"两边都折简体"统一解决，不需要它。

### 字面通道保持原样（关键）

折的只有查询词 `q` 和内容 haystack。**`token`（原始输入）不折**，所以：

| 键入 | 详情报点 | 期望 |
|---|---|---|
| `馬` | **U+99AC** | 不是简体 U+9A6C ✅ |
| `車` | **U+8ECA** | 不是 U+8F66 ✅ |
| `乾` | **U+4E7E** | 不是 U+5E72 ✅ |
| `干` | U+5E72 | 反向没被折走 ✅ |

单字符三形式直查、`parseCodePointQuery`、SYMBOL_MAP 的 `char === q`、`resolveSeq` 一律仍吃原始 `token`。
