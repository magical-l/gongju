## 1. 主角标签是怎么定下来的

起点是「用『心』标签截个屏」，用户否了（内容不够杂）。扫遍全树 300 个语义节点后，判据收敛成：

- **①** 成员里天然有 emoji + 双模 + 黑白图符
- **②** 跨文字系统
- **③** 黑白字符要有趣（但不能偏门到需要解释）
- **④** 左树那一小片（父级 + 兄弟姐妹 + 叔伯）读起来像正经分类

试过又否掉的：`货币标志`（我以为「钱号是从各文字系统借来的」——**错**，它们是后世生造的，只是被分配进那些区块）、
`天气`（①最齐但②③弱）、`人形图示、火柴人`（③最强，但 26 个里有 3 个是豆腐块）、
`变体符号/带圈`（唯一成员天然七类齐的，但首屏只出拉丁字母，其余要翻页）。
最后定 **`自然 / 生物 / 植物 / 花朵`**。

⚠️ **网格是按码点顺序分页的**（`CAP=100`，`cardWindow()`），所以一个标签的首屏往往只有一种文字——
**想在一屏里看到混搭，唯一办法是让成员码点散开**（这个标签是用户手挑出来的，天然散）。

## 2. 「花朵」的策展

**成员**：用户手挑 + 补名。145 个 → 剔掉非花与豆腐块后 **65 个**，全部可显示。

**剔非花靠 `Unikemet` 的 `kEH_Desc`，不靠眼睛。** 描述里有没有 `flower` / `floret` / `blossom` / `bud`，
直接决定去留——比看图形快且不会看走眼（我按眼睛判错过好几处：把 `𓇖` 沙漠植物看成没花，
其实描述写着「flowers on every branch」）。剔出去的 20 个挪到 `植物` 本级。

**渲染不出来的整块移走。** 埃及象形**扩充-A（U+13460–U+143FF）共 80 个**：本机没有字体（项目自带的
Noto Sans Egyptian Hieroglyphs 只覆盖基础区），而且**从没被命名过**（见 §5）。全部移出「花朵」，最后直接删掉。

**语境名**：不表示具体花种的，用户定的规则是叫「XX花朵」（实心花朵 / 空心花朵 / 螺旋花朵 / 四瓣花朵…）；
具体花种才用花名（鸢尾花 / 向日葵 / 玫瑰花 / 莲花 / 樱花 / 梅 兰 菊）。

## 3. 迷你页面（缩略图）

**260×166**（首页卡片图区净尺寸）× 3 = 780×498。左标签树 80px + 右 5×5 网格。

树的四个要求（用户提的）：**窄**、**行铺满列**、**选中不把文字挤右**（用 `box-shadow: inset` 不用 `border-left`）、
**三角收展符保留**。数字取自真实页面（自然 414、生物 265…），不按码点估——两者差几十。

**踩的两个坑：**

1. `font-variant-emoji: text` **只加在 `.char-grid .char .variant.text` 和 `.vs-text` 上**，不是整块网格。
   我一开始加在整块上，把 emoji 全压成黑白了。网格里的真 emoji 是**彩色**的。
2. 名字要按真实页面的顺序取：**该标签子树里最深的已命名组 → 条目级主名 → 直译名**。
   我的挑选页只查了后两层，于是显示的是直译名（用户一眼看出来）。

另外 `꧁ ꧂` 那两个字号的**墨迹（20×19）远大于字号框**，会顶出格子压到邻居。做成三条对比（放开 / 裁剪 / 单独降字号）
后用户干脆**换掉了它们**，理由是那种溢出「可能让用户以为我们有 bug」。

## 4. 星号族命名统一（21 条）

Dingbats 的 `U+2722–U+274B` 一族里，老的用「水滴 / 芒 / 角 / 螺旋 / 重」，新的（用户刚定的 ❃）用
「泪滴 / 辐条 / 尖 / 重…」。统一成后者，逐条按官方名写死：

```
水滴→泪滴   SPOKED→辐条   POINTED→尖   HEAVY→粗
```

⚠️ **不能盲替换**：`芒` 既可能是 `POINTED` 也可能是 `SPOKED`（✺ 是 POINTED 该给「尖」）；
`✩` 的「加重」来自 `STRESS` 不是 `HEAVY`，动了就错。

## 5. 一个必须记住的边界：别拿 emoji 的引擎去验非 emoji 的字

我一度拿 `emoji词表.translate` 去跑这批星号，算出「四泪滴辐条星号」这类结果，据此说数据「搁浅」了。
**全错**：`✢ ✦ ✵ ✻ ✽ ❁ ❃ ✿ ❀ ❊ ❋` **都不在 `emoji-test.txt` 里**，根本不是 emoji。

顺着查下去：两套词表（`emoji词表.py` / `译名词表.py`）都没有 `PROPELLER`/`CENTRE`/`RECTILINEAR`/`SIXTEEN`/
`SPOKED`/`TEARDROP`/`PINWHEEL`/`FLORETTE`，非 emoji 那套的入口 `letter_zh()` 对这些名字**直接返回 `None`**。

**所以「四水滴芒星号」这类名字从来不是引擎产的，是人工起的**——它们没有「本该算出什么」，
「引擎 == 数据」这条**本来就不该套在它们身上**。那批英文没译，是因为那些词只出现在这几个冷门名字里
（`CLUB-SPOKED` 全库 1 次、`PROPELLER` 2 次），做词表时没人碰过。

**判据**：`引擎==数据` 只用来抓「**数据写错了**」（`重黑心`→`粗实心心形`）；
**数据比引擎好时，数据就是对的**（✢ 的「四水滴芒星号」比引擎能给的任何东西都清楚）。

## 6. 词表改动（根因）

| 词 | 原 | 现 | 为什么 |
|---|---|---|---|
| `ROSETTE` | 莲座 | **圆花饰** | `ROSETTE` = 一圈花瓣的装饰性圆花，不特指莲；「莲座」是佛座的词，纯错译 |
| `ROSE` | 玫瑰 | **玫瑰花** | 与郁金香/向日葵这类并列读着齐；连带删 🌹 的冗余别名「花」 |
| 三条整名短语 | — | — | `HEAVY BLACK HEART` / `HEAVY HEART EXCLAMATION MARK ORNAMENT` / `LIGHT BLUE HEART`（见 §七「短语截胡」） |

## 8. 教训

1. **别拿错引擎下结论。** §5 那次我差点让用户去"修"一个不存在的问题。
2. **「搁浅」有适用边界**：它描述的是「引擎本该产出、但被冻结了」；对**从来就是人工名**的那批，这条不适用。
3. **给用户看结论前先列清单。** 「15 条」那句我说得含糊且数字也是错的，用户直接要「你好歹列出来」。
   数字必须是自己数出来的，不是印象。
4. **眼睛会骗人，描述不会**（§2 的 Unikemet 判据）。
