字体栈与字符兜底

双模字符
	同一个码位可能有多种呈现。☺ ♥ ▶ ▪ © 这类字符既能走文本形态（单色），也能走 emoji 形态（彩色）。
	本页的选择：让它们默认渲染成单色，跟普通文字一致。要彩色得显式加变体选择符 U+FE0F。

	⚠️ **这条只落在「文本变体」那个小标签上**，不是整页口径（2026-10-09 实测）：
	`font-variant-emoji: text` 只写在 `.vs-text` 和 `.char-grid .char .variant.text` 上；
	**网格卡片那层 `.char-symbol` 是 `normal`**，字体栈 `Arial, "Segoe UI Emoji", "Noto Sans Symbols 2"…`——
	所以卡片上的双模字符**会被 Segoe UI Emoji 接管、渲染成彩色**，只有那个小标签是强制单色的。
	⚠️ 照「整块都强制单色」去复刻页面，会做出一屏黑白 emoji（复刻缩略图时踩过）。

没有字体覆盖全部 Unicode
	本页字体栈里五个字体的实际覆盖（读字体文件的 cmap 表，2026-09-20 实测）：
		Arial  3,506 码位  2.34%
		Segoe UI Emoji  2,025  1.35%
		Noto Sans Symbols 2（页面自带）  2,955  1.97%
		Segoe UI Symbol  7,536  5.03%
		Consolas  2,489  1.66%
		五个加起来（并集）  11,411
	参照：Unicode 15.1 已分配码位共 149,813。
	各字体补了哪些别家没有的（独有贡献，同一算法实测）：
		Segoe UI Symbol  3,869
		Arial  1,179
		Noto Sans Symbols 2  601
		Segoe UI Emoji  226
		Consolas  9
	（2026-09-20 去掉了 Lucida Sans Unicode：独有贡献 0，它覆盖的 1,753 个码位其余字体全都有，并集不变。）
	五个加起来才一万出头，所以渲染一个字符要按顺序问一排字体，谁先有字形就用谁。这就是字体栈。

栈穷尽之后：系统字体链
	栈里六个都没有字形时，浏览器还会继续往系统字体链里找——按字符所属的文字系统挑一个系统默认字体。这一段在栈外，页面控制不了，但得知道它存在。
	本机实测命中（2026-09-16，字体栈与页面完全一致，lang="zh-CN"）：
		中 / あ  →  Noto Sans SC
		한       →  Malgun Gothic
		ཀ        →  Microsoft Himalaya
		ก        →  Tahoma
		𠀋       →  SimSun-ExtB
	规模：本机 229 个字体文件合起来覆盖 154,279 个码位，其中 142,868 个（92.6%）是栈覆盖不到、只能走系统链的。按类别：
		汉字（统一表意 + 扩展 A/B/C-F/G-H）  97,064  68.0%
		谚文音节（韩文）                      11,184   7.8%
		彝文、藏文、泰文、天城文等各语种文字
		少量符号与变体选择符
	所以「中文能正常显示」不是这个字体栈的功劳，是系统链兜的——换一台没装中文字体的机器就会全是豆腐块。
	反过来，阿拉伯文、希伯来文、希腊文、西里尔文其实都在 Arial 里，属栈内覆盖，不需要系统链接手（实测 ا 命中 Arial）。

浏览器怎么用字体栈
	font-family 给一串字体名，浏览器从头逐个问「你有这个字形吗」，用第一个有的。
	「泛型」（sans-serif / serif / monospace）不是某个具体字体，是让浏览器取系统默认。浏览器拿到泛型会展开成一条系统回退链，而不是当成一个普通候选。
	所以如果把泛型放开头，后面显式列的字体永远轮不到——泛型自己就把字符消化掉了。

	这件事的具体机制（本机实测）：系统回退链按文字系统挑默认字体，中文挑的是 Noto Sans SC。它覆盖 30,890 个码位，除了 20,976 个汉字，还顺手包含了杂项符号区 U+2600-27BF 的 88 个和 CJK 符号区 U+1F200-1F2FF 的 58 个——⚽ 🈚 🆎 🉑 就在里面，而且它们都不在 Arial 里。
	所以泛型打头时，这 146 个符号被 Noto Sans SC 拿走渲染成单色，后面显式列的 emoji 字体永远轮不到。
	它不碰真 emoji 区（U+1F300-1FAFF 覆盖 0 个），所以 😀 🏀 这类一直正常——问题只藏在那一百多个符号里，小到不容易被发现。这也解释了为什么"系统文字字体也覆盖的那批 emoji"才会出问题。

	⚠ 顺序**只在「多个候选字体都覆盖同一个码位」时才起作用**——只被一家覆盖的码位，排第几都归它。
	所以顺序不是覆盖率问题（并集与顺序无关），是「冲突时谁赢」问题。

	栈的顺序（2026-09-20 起）：
		1 一个文字字体（Arial）打头。它不含 emoji 字形，双模字符留在文本形态，真 emoji 继续往下落。
		2 系统 emoji 字体（Segoe UI Emoji）。真 emoji 在此落定。
		3 页面自带的符号字体（Noto Sans Symbols 2）。
		4 系统符号字体（Segoe UI Symbol）。
		5 泛型兜底。
			6 页面自带的埃及象形字体（Noto Sans Egyptian Hieroglyphs）——**按需**，默认不在栈里，见「埃及象形字体」一节。

	为什么自带字体排第 3，而不是从前的「紧挨泛型之前」（2026-09-20 改，起因见 任务/·017）：
		它与第 4 名 Segoe UI Symbol 重叠 2,169 个码位，太玄经区段（U+1D300-1D35F）整个 87 个都在里面。
		Segoe UI Symbol 给这一段画的是 Unicode 早期提案的**错版字形**——提案 N2416 把 U+1D301/U+1D302/
		U+1D303 三个双爻的字形互相排错，官方在 Amendment 1 里改正了，这个字体没跟。
		把自带字体提到它前面，这 2,169 个码位就改由自带字体渲染（与官方码表一致）。
	为什么不能再靠前（放到 emoji 之前）：
		自带字体与 Segoe UI Emoji 重叠 715 个码位，其中 267 个在 emoji 区（🌍 🌕 🎉 一类）。
		再提前会把它们从彩色 emoji 抢成单色符号，与「只有双模字符走单色」那条口径相反。

	设计生效的实测证据（同一批测量里取的）：
		☺ → Arial          双模字符落在文字字体上，没被 emoji 字体抢走
		⚽ → Segoe UI Emoji  emoji 正确落到 emoji 字体
		😀 → Segoe UI Emoji
		𝌁 → Noto Sans Symbols 2（页面自带）  太玄经双爻，靠第 3 位避开 Segoe UI Symbol 的错版字形
	列表区和详情区共用同一个栈，两区渲染一致。栈的权威值在页面脚本里，挂载时写入；样式表里那份是挂载前的兜底，改栈时两处要同步。

页面自带的字体
	符号页随页面加载一份覆盖很广的符号字体，放在栈里第 3 位（系统 emoji 之后、系统符号字体之前，理由见上）。
	效果：系统里没有的符号，本页也能显示。
	注意别把它想成「用户装的」——它是随页面来的，对方打开本页自动就有。只有把字符复制到本页之外去用，才需要对方自己装字体。

埃及象形字体（2026-10-04 加）
	第二份随页面带的字体：Noto Sans Egyptian Hieroglyphs（OFL，572KB），覆盖埃及象形基本区 U+13000-1342F，1072/1072 全覆盖。
	此前这一段只有 Windows 靠系统自带的 Segoe UI Historic 看得见（实测它覆盖 1071/1072），macOS / Linux 都不带——内置是为了跨平台一致。
	⚠️ 它覆盖不了扩展区 U+13460-143FA（0/3995，连 Noto 也没有）——那 3995 个码位至今没有字体，见 任务/✓038。

	**它不常驻字体栈，由 JS 按需追加**（`符号.js` 的 `viewHasEgypt` → `setFontStacks(FALLBACK_SYMBOL_FONTS, v)`）：
	当前实际会渲染的成员（网格 `gridItems` / 概览各段 `preview` / 搜索结果 / 详情与操作记录）里，有码位落在 U+13000-1342F 时，才把它加到 `sans-serif` **之后**；否则整条栈里没有它。
	效果：不看埃及象形的人**一个字节都不下**（实测：默认视图不请求；搜「水波」出 7 个埃及字符时才请求）。

	为什么不靠 `unicode-range` 挡（两处都实测过）
		两份 `@font-face` 都写了 `unicode-range`，但**它挡不住下载**：只要字体族出现在栈里，页面一加载就会被取下来——实测该页一个埃及字符都没有、也没有任何栈内字体盖不住的字符，照样下 572KB。
		⚠️ 我一度把字体排在 `sans-serif` 之前，还拿「注入到独立 div」的小实验当证据、说「排到后面的就不下」——**真页面上不成立**。小实验不等于真实页面结论。
		真正生效的是**条件加栈**：栈里没有它，就无从触发。

	⚠️ CSS 静态那份 `--sym-font-stack` **故意不含埃及族**（只留 JS 按需追加）——「两处必须同步」这条在**这一个族上是有意破例**的，别顺手同步回去。

渲染不出来时的两条提示
	判断两件互相独立的事：
		系统默认字体链能不能渲染——不含页面字体栈，问的其实是「复制到别处还看得见吗」
		页面自带的字体收录了它没有
	组合出两条提示，互斥，永不同时出现：
		自带的也没有 → 「当前字体不支持」，显示在名字下方
		自带有、系统渲染不出 → 说明本页用自带字体显示，显示在名字上方
	第二条是推出来的：系统链渲染不出而自带有，说明栈里排在它前面的那几个系统字体也都不行，渲染一定靠它。
	实测：U+1F900、U+1FA00（国际象棋符号）会触发提示；系统能渲染的（如 U+1F600）两条都不出现。

详情区的字体切换
	详情区可以手动选一个字体预览。**选中后强制只用那个字体，不走栈、不走 fallback**——这样切换才看得到真实效果，否则没覆盖的字符被栈兜住，看不出差别。
	「加载本机字体」只扩充可选的列表，**不改渲染栈**。

判定要看实际渲染结果
	查字体的收录表只能知道「有没有收录」，回答不了「渲染出来是不是豆腐块」。
	做法是拿保证没有字形的私有区码位当参照比出豆腐块模板，再逐像素比对。
	⚠️ **canvas 里量 ≠ 页面里渲染**：canvas 的字体属性对超长 font-family 列表解析异常。检测必须用 DOM 探针。
	⚠️ **浏览器缺字形会自动 fallback，几乎不显示 .notdef**——所以"强制只用某字体"时，未覆盖的字符显示的是系统兜底字形，不是豆腐块。

已知遗留
	Unicode 16/17 有 7 个 emoji 字符，本机这六个字体一个都没有，必然显示为豆腐块：
		🛘 U+1F6D8 滑坡
		🪊 U+1FA8A 长号
		🪎 U+1FA8E 宝物箱
		🫈 U+1FAC8 多毛生物
		🫍 U+1FACD 虎鲸
		🫪 U+1FAEA 扭曲脸
		🫯 U+1FAEF 打斗云
	这是字体没收录，不是栈排错。

	另一件：本机把 Noto Sans Symbols 2 也装进了用户字体目录，所以系统链也可能命中它。在这台机器上验证「系统没有、靠页面自带字体显示」是不可靠的，要去没装该字体的机器上验。

改这块时注意
	要查某字符实际命中哪个字体，用浏览器调试协议的字体查询。document.fonts.check() 不能用：它装的是页面用 @font-face 声明过的字体，字体名不在这个集合里就直接返回 true，而系统字体从来不在集合里。
	字体回退问题要用本机真实 Chrome 验证。自动化测试自带的 Chromium 版本固定，与本机 Chrome 版本不同；字体回退行为随 Chrome 版本变过，会得出相反结论。
	字体查询返回的字形数不能判豆腐块：缺字形时它报的是该字体的 .notdef，照样是「1 个字形」（实测 🛘 报 Arial [1 字形]，其实是豆腐块）。
	渲染宽度等于一个字符宽不等于豆腐块——全角字符本来就占一个字符宽，那是正常字形。
	改完 bump 页面资源版本参数（惯例 ?v=YYMMDD），否则浏览器拿缓存。
