# 买房费用计算器：一次性费用 <100元 忽略并灰显

## 动机

一次性费用表里登记费（80元）等小额费用数额微小，却与几万、几十万的税费同列，干扰对「现金支出合计」的直观判断。用户要求：金额 <100元 的费用项忽略（不计入合计），该行文字灰显提示。

## 变更（`买房/买房费用.html`）

| 项 | 说明 |
|----|------|
| 阈值常量 | 新增 `FEE_IGNORE_WAN = 0.01`（100元 = 0.01万元，全表金额单位万元） |
| 判定方法 | 新增 `feeIgnored(wan)`：`wan < FEE_IGNORE_WAN` |
| totalCash | 7 项一次性费用逐个用 `count(wan)` 包装，忽略项按 0 计；首付、feeItems 不受影响 |
| 行灰显 | 7 个费用行（增值税/个税/契税/中介费/维修基金/印花税/登记费）加 `:class="{ mute: ... || feeIgnored(x) }"`，复用已有 `.mute`（#c0c4cc） |
| 占比列 | 被忽略行显示「—」，正常行显示「x%」 |

## 设计决策

- **「忽略」= 不计入现金支出合计**（用户确认）。语义：灰显即表示"没算进去"。
- 阈值 100元：登记费默认 80元 恰在其下，印花税免付为 0 也落入——都是用户感知上的"零头"费用。
- 首付行不适用（非费用项，且恒大于阈值）。
- 判定统一用 computed 值（vat/pit/deedTax/agencyFee/maintenanceFund/stampDuty/registrationFee），与 totalCash 求和口径一致；登记费占比列原用 `regFeeAmount`，本次统一为 `registrationFee`（fixed 模式下二者相等）。

## 踩坑记录

1. **占比列「—%」残留百分号**：模板写成 `{{ cond ? (x/totalCash*100).toFixed(n) : '—' }}%`，`%` 在三元表达式外，被忽略行渲染成「—%」。修复：`%` 移进真分支（`toFixed(n) + '%'`），假分支纯「—」。此写法是页面既有模式，本次让该坑首次可见。
2. **Edit 工具 em-dash 匹配失败**：html-editor 用 Edit 对含「—」（U+2014）的 7 行全部报"未匹配"（Grep 显示内容精确存在），降级用 Node 字符串替换完成（替换前校验模式计数==1）。根因未定位，疑与文件编码/BOM 相关。

# 同日补充：一次性费用表斑马纹

## 变更（`买房/买房费用.html`）

`.fee.card` 独立新增规则 `& tbody tr:nth-child(even) { background: #f5f7fa; }`，隔行浅灰。**只加一次性费用表**，贷款表 `.loan.card` 不适用（共享样式块 `.fee.card, .loan.card` 未动）。tfoot 合计行在 tbody 选择器命中范围外，无需处理。

## 设计决策

- 颜色 `#f5f7fa`（Element Plus 默认斑马纹色，浅灰不刺眼）；灰显行（忽略的小额费用）文字仍为 `.mute` 灰，与斑马背景叠加无冲突。
- 斑马纹与「忽略并灰显」逻辑正交：结构性视觉（隔行背景）与语义性视觉（忽略行灰字）分开表达。

# 同日补充（三）：两表表头浅色样式

## 变更（`买房/买房费用.html`）

`.fee.card, .loan.card` 共享块内 `& th`：`font-weight: 500` → `600`，新增 `background: #ecf5ff; color: #303133;`。两个表（一次性费用、贷款）表头同时生效，th 上的对齐类保留。

## 设计迭代

- 初版按用户选项做**深色表头**（`#303133` 底 + 白字），用户反馈「颜色太深了！没必要」→ 改为浅蓝底 `#ecf5ff` + 深灰字 `#303133`。
- 教训：整行深色背景在数据密集的表上显得笨重；表头只需「略区别于正文 + 加粗」即可，浅色底 + 深色字是安全形态。颜色选择先给用户两个方向（深/浅）预览再动手，避免来回。

# 同日补充（四）：登记费改「元」单位 + 设定列输入框收窄

## 变更（`买房/买房费用.html`）

| 项 | 说明 |
|----|------|
| 字段单位 | `regFeeAmount` 语义万元→元：data 0.008→80；`resetRegFee` 同步；fixed 分支 computed `registrationFee` 改为 `regFeeAmount / 10000`（元→万元，供合计/占比用） |
| 输入框 | 定额输入 `:step 0.001→1`、`:precision 3→0`、后缀「万元」→「元」 |
| 金额列 | `regFeeAmount.toFixed(3)万` → `(registrationFee * 10000).toFixed(0)元`（改用 computed，与占比列口径一致） |
| 输入框宽度 | 「设定」列（每行第4个 td）所有 el-input-number 120→**96px**，规则 `.fee.card { & tbody td:nth-child(4) .el-input-number { width: 96px } }` |
| 缓存版本 | `STORAGE_KEY` 2026v3→**2026v4** |

## 设计决策

- 登记费只有 80元，用万元显示成 0.008 既别扭又需要 3 位小数；改元后输入框、金额列、后缀统一「元」，更符合直觉。
- 金额列改用 `registrationFee`（computed）而非 `regFeeAmount` 原值：顺带修正 percent/exempt 模式下金额列显示 raw 定额、与占比列口径不一致的老毛病——exempt 时显示 0元（并灰显），percent 时按费率算，与其他费用行行为一致。
- 宽度 96px：实测最长内容（首付 `120.00万元`、维修基金 `元/㎡`）均不裁切；选择器 specificity 足够覆盖 Element Plus 默认 `--el-input-number-width`（150px），无需 `!important`。

## 踩坑

- **字段单位变更必须失效旧缓存**：`regFeeAmount` 从万元改元是数据形状变化，旧用户 localStorage 里的 `0.008` 若被当元读取，登记费会静默变成 0元。沿用 v2→v3 惯例 bump STORAGE_KEY 使旧 key 失效，而非在 `created()` 写迁移补丁。
