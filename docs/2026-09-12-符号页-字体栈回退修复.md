# 符号页：字体栈回退修复（v1.34.0）

日期：2026-09-12
状态：已实施

## 背景

用户报「emoji 标签下的字符默认显示成 text 模式而非 emoji 模式」。举例 `⚽`（U+26BD）看上去是按 **Consolas** 渲染的（单色轮廓字），而按预期它应该落到 `Segoe UI Emoji` 出彩色。注意 `😀`、`🏀` 这类一直正常 —— 出问题的是一批**系统文字字体也覆盖**的码位。

## 一、根因

`符号/符号.js` 的 `buildFontStack()` 把**泛型** `sans-serif` 放在渲染栈**首位**，注释还写着「sans-serif 触发系统回退链」，把这件事当成了特性。

问题在于 Chrome 对**泛型字族**的处理方式与命名字体不同：

- 命名字体（`"Segoe UI Emoji"`）：**缺字形**就跳到栈里的**下一个命名项**。
- 泛型字族（`sans-serif`）：**不是**"某个字体的别名"，它按**脚本**解析，会展开成**整条系统回退链**。链里任何一个覆盖该码位的字体都能赢，与栈里后续项无关。

在装了 `Noto Sans SC` 的中文机器上，`⚽` `🈚` `🆎`～`🉑` 这类字符被 `Noto Sans SC`（**文字字体，单色**）拿下，排在第二位的 `"Segoe UI Emoji"` 永远轮不到。

## 二、实测证据

用 CDP `CSS.getPlatformFontsForNode` **逐字符**读实际命中字体（不是看截图猜）：

| 实验 | 对象 | 旧栈（`sans-serif` 置首） | 新栈（`Arial` 置首） |
|---|---|---|---|
| A | emoji 根下 **1184 个单码位字符** | 只有 **74/100** 落对（落 Segoe UI Emoji） | **1177/1184** 落到 `Segoe UI Emoji` |
| B（对照） | 同一页面强制不同栈，量 **207 个双模字符的 text 变体**（FE0E） | **207/207** 落 `Noto Sans SC` | 落 `Arial` / `Segoe UI Symbol`，**0 个落到 emoji 字体** |

实验 B 是关键的**对照**：证明这次改动**不动双模机制** —— text 变体仍然走文字字体，没有被"顺手"染成彩色。

### 为什么打头用 `Arial` 而不是 `"Segoe UI Emoji"`

直觉上"要让 emoji 显示成 emoji，就把 emoji 字体放第一位"。这是**另一个错**：`☺ ♥ ▶ ▪ ©` 这类是 **Unicode 默认文本呈现**的双模字符（Default_Emoji_Presentation = No），用 emoji 字体打头会把它们也默认渲染成彩色 emoji。

`Arial` 恰好两端都对：

- **不含** emoji 字形 → emoji 字符继续往下落到 `"Segoe UI Emoji"`（彩色）；
- **含** `☺ ♥ ▶ ▪ ©` → 这些默认文本呈现的字符停在 Arial（单色），各归其位。

## 三、「比较久之前是怎么对的」——回归调查（重要）

用户追问"以前明明是好的"。结论：**这是 Chrome 版本行为变化导致的回归，不是数据或代码写错。**

**同一个旧栈、同一台机器**逐字符实测：

| 浏览器 | `⚽` `🈚` `🆎` 判给 | 对错 |
|---|---|---|
| HeadlessChrome **147** | `Segoe UI Emoji` | 正确 |
| Chrome **152** | `Noto Sans SC` | 错误 |

**历史线**：

- `dde37bc`（2026-08-19「符号页：豆腐块检测与字体信息」）把栈从 CSS 硬编码的 `"Noto Sans Symbols 2", "Segoe UI Symbol", sans-serif` 改成 **`sans-serif` 置首**，提交信息自述「系统默认优先由 sans-serif 置于栈首实现」—— **在当时是实测成立的**。
- 该回归**只影响"系统文字字体（Noto Sans SC）也覆盖"的那批 emoji**（`⚽🈚🆎`～`🉑`），`😀🏀` 这类一直正常 → 所以长期没被发现。

**字体安装时间排查**（排除"字体是后装的"这条假设）：`C:\Windows\Fonts\NotoSansSC-VF.ttf` 创建时间 **2025-06-30 15:20**，与 `msyh.ttc` 同批（是系统铺字体目录的时间），**远早于 8/19** → 排除。

**诚实保留**：147 vs 152 的对比**只能算旁证** —— headless vs headed、构建方式、profile 都不同，要钉死需跑桌面版旧 Chrome。但**修复的必要性不依赖这个结论**：泛型置首本身就是把行为交给不可控环境（浏览器版本 / Windows 更新 / 系统装了什么字体）。

**外部佐证**：

- Chromium 128+ 在中文环境优先选 `Noto Sans SC`（前提：本机装了它）。
- Windows 更新与**商店版应用宝**都会静默装入该字体。

### 复现与验证方法

用 CDP 逐字符读实际命中字体（截图肉眼判断不可靠）：

1. 真实 Chrome 开 `符号.html`（`--remote-debugging-port`），取到目标节点。
2. 调 `CSS.enable`，对每个字符对应的 DOM 节点调 `CSS.getPlatformFontsForNode({nodeId})`，取 `fonts[].familyName` 作为**实际命中字体**。
3. 遍历 emoji 根下全部单码位字符，统计"命中 `Segoe UI Emoji`"的比例，即第 1 节表格里的 1184 / 74 / 1177 三个数。
4. 对照实验 B：同一页面用 JS 覆盖 `--sym-font-stack` 为旧/新两版，量 207 个双模字符的 FE0E 变体，看是否落到 emoji 字体（**应为 0**）。

## 五、已知未解（7 个字符，非本次回归）

| 码位 | 情况 |
|---|---|
| `U+1F6D8 / 1FA8A / 1FA8E / 1FAC8 / 1FACD / 1FAEA / 1FAEF` | Unicode 16/17 新增 emoji，本机 `Segoe UI Emoji` **无字形** |

改前落 `Noto Sans SC` 的 `.notdef`，改后落 `Arial` 的 `.notdef` —— **前后都是豆腐块**，与本次回归无关。用户裁定**不为这 7 个字符引入字体文件**。

## 六、副作用（如实写）

修复方向正确，但**不是零代价**：

1. **拉丁字母 / 数字 / 希腊字母 / 货币 / 标点 从 `Noto Sans SC` 变成 `Arial`** —— 旧栈下 `sans-serif` 在这台机器上就解析成 `Noto Sans SC`，置首换成 Arial 后这批字符的观感随之改变。
2. **双模字符的 emoji 变体在非 emoji 标签下也变彩色了**（如「箭头」标签里的 `⬅️`）。这是同一个修复的延伸效果（VS16 让字符走 emoji 字体），属预期方向，但用户会看到页面整体"彩色点变多"。

## 七、教训

1. **泛型字族不是"某字体的别名"**。`sans-serif` / `serif` / `monospace` 按脚本解析、会展开系统回退链 —— **放栈首等于把行为交给环境**（浏览器版本、系统更新、装了什么字体），不可控。
2. **判断某字符实际用了哪个字体**：CDP `CSS.getPlatformFontsForNode`。**`document.fonts.check()` 对任意字体名都返回 `true`，无效** —— 别拿它当判据。
3. **Playwright 自带 Chromium ≠ 真实 Chrome 的字体回退**。字体类问题**必须在真实 Chrome 复现**（本次 headless 147 与 Chrome 152 判决相反，就是活例）。
4. **排查「以前明明是好的」别只怀疑数据和代码** —— **浏览器版本会改行为**。先做"同环境新旧对比"，再决定改不改数据。
5. **模糊的注释会掩护 bug**。原注释「sans-serif 触发系统回退链」把不确定行为写成了设计意图；写注释时若说不清"为什么这么放"，往往就是没想清楚。
